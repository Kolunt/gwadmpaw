# Админ-панель

Раздел `/admin/*` использует **отдельный layout** (`templates/admin/base.html`), не наследует публичный `base.html`.

## Тема и интерфейс

- На всех админ-страницах задано `data-theme="admin"` (тёмно-бордовая тема).
- Переключатель светлой/тёмной темы **отключён** — админка всегда в admin-theme.
- В сайдбаре админки — единое меню разделов; пункт «На сайт» ведёт на главную публичного сайта.
- В публичном сайдбаре у пользователей с ролью `admin` — **одна** ссылка «Админ-панель» на `/admin/`.

## Интеграции (настройки)

В `/admin/settings` → **Интеграции**: DaData, SMTP, Telegram, GWars. При включённой и проверенной DaData на сайте появляются подсказки адреса в модалке регистрации на мероприятие и в редактировании профиля. Подробнее: [doc/dadata.md](dadata.md).

## Мероприятия: создание и редактирование

| Действие | Маршрут |
|----------|---------|
| Создать | `/admin/events/create` |
| Редактировать | `/admin/events/<id>/edit` |

Карточка `.event-form` без внешнего padding: отступы только у внутренних `.form-section` и `.form-actions` (`--layout-inner`), без дублирования с глобальными стилями рассылок.

В блоке **«Этапы мероприятия»** даты и время задаются в **локальном времени браузера** администратора. При отправке формы значения уходят в формате `YYYY-MM-DDTHH:MM` (поля `stage_<тип>_start` / `stage_<тип>_end`); сервер сохраняет их в SQLite как `YYYY-MM-DD HH:MM:SS`.

Интерфейс: нативные поля `datetime-local` и компактная кнопка «календарь» (📅) в одной строке с полем (включая mobile), которая вызывает `HTMLInputElement.showPicker()` там, где браузер поддерживает API. Без JavaScript поля остаются рабочими — можно кликнуть по полю или по встроенной иконке календаря (Chromium). Скрипт: `static/js/admin-event-form.js`, подключается только на странице формы мероприятия.

## Дашборд (`/admin/`)

Метрики собираются в `gwadm/services/admin_dashboard.py`.

| Метрика | Определение |
|---------|-------------|
| Всего участников | `COUNT(users)` |
| Рейтинг + / − | строки в `user_rating_cache` с `total_points > 0` / `< 0` |
| Без участия | пользователи **без** записей в `event_registrations` |
| Онлайн | `count_online_users()` — `last_seen` / `last_login` за последние 15 минут |
| Очередь рассылок | `broadcast_queue` со статусом `pending` или `processing` |
| На ревью | сумма неутверждённых участников на мероприятиях в стадии `lottery` (после наступления даты начала жеребьёвки) |
| Подарки (всё время) | агрегат по `event_assignments`: полный цикл = отправлен и получен |
| Подарки (последнее событие) | то же для **последнего завершённого** мероприятия |
| Кэш рейтинга | заполнен ли кэш и `MAX(updated_at)` из `user_rating_cache` |

### Последнее завершённое мероприятие

Функция `get_last_finished_event()` в `gwadm/services/events.py`:

1. Перебирает `events` с `deleted_at IS NULL`.
2. Оставляет только те, где `is_event_finished(event_id)` — этап `after_party` уже закончился.
3. Выбирает мероприятие с **максимальной** датой `after_party.end_datetime` (не по `created_at`).

Карточки дашборда ссылаются на соответствующие разделы: метрики участников (рейтинг +/−, без участия, онлайн) — на `/admin/users?filter=…` (`rating_positive`, `rating_negative`, `never_participated`, `online`); рассылки и ревью — на `/admin/broadcasts`, `/admin/events` и т.д.

## Участники: блокировка

На `/admin/users/<user_id>/edit` — форма блокировки с обязательной причиной и разблокировка. Поведение для заблокированного на сайте: [doc/user_blocking.md](user_blocking.md).

## Настройки: данные пользователей

Вкладка **«Данные пользователей»** на [`/admin/settings`](/admin/settings) (`#profile-data`):

| Колонка | Смысл |
|---------|--------|
| **Собираем** | Поле показывается в профиле и в сценарии регистрации на мероприятие |
| **Обязательно** | Должно быть заполнено для завершения регистрации (только если сбор включён) |

Политика хранится в `settings.profile_data_policy` (JSON). Логика — [`gwadm/services/profile_fields.py`](../gwadm/services/profile_fields.py).

Для группы **контакты** дополнительно действует правило: среди полей с включённым сбором нужен **хотя бы один** заполненный канал (email, телефон, мессенджеры, Max).

Подробнее о канбане прогресса обмена: [fulfillment.md](fulfillment.md).

## Настройки рейтинга (`/admin/rating-settings`)

Вкладка **«Контактная информация»** задаёт очки за заполненные каналы связи (Telegram, WhatsApp, Viber, **Max**). Ключ `rating_contact_max` добавляется миграцией 010.

После сохранения профиля участником (форма или API), если изменены поля `telegram`, `whatsapp`, `viber` или `max`, приложение сразу вызывает синхронизацию снежинок за контакты и обновляет кэш рейтинга (`user_rating_cache`).
